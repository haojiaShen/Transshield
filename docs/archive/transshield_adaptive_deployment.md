# Transshield 自适应部署方案：不同硬件条件下的配置指南

最后更新：`2026-05-12`

## 背景

在实际部署中，不同医院的服务器硬件条件差异很大。城市三甲医院可能拥有高性能服务器集群，
而乡村卫生院可能只有普通办公级服务器。Transshield 需要在不同硬件条件下，通过调整关键参数，
在精度和效率之间取得最优平衡。

## 核心调参杠杆

### 1. Transformer 深度（影响最大）

模型共有 12 个 Transformer Block。动态剪枝在第 3、6、9 阶段执行，到第 9 阶段后，
活跃 token 数量已经很少（约 67 个，原始 196 个的 34%）。因此后面的 Block 计算量虽然绝对值不大，
但在安全多方计算环境中，每一层都需要两方协议交互，通信开销不可忽略。

| 深度 | 跳过的 Block | 明文精度（参考） | 安全推理精度 | 推理时间 |
|------|-------------|-----------------|-------------|---------|
| depth12 | 无 | 91.98% | 92.44% | ~21s/sample |
| depth10 | 10-11 | 91.41% | ~91% | ~17s/sample（预估） |
| depth8 | 8-11 | ~89% | ~88% | ~14s/sample（预估） |
| depth6 | 6-11 | ~85% | ~83% | ~11s/sample（预估） |

> 注：depth10 的明文精度 91.41% 已通过实验验证（`run_secure_pruning_smoke8_batch8_depth10.sh`）。
> depth8/6 为基于剪枝 token 数量的线性外推预估值，需实际验证。

### 2. 批量大小

安全推理中，批量大小主要影响 SPU session 的复用效率。批量越大，session 启动开销被摊薄越多。

| 批量大小 | sec/sample（nonisolated） | 说明 |
|---------|--------------------------|------|
| batch=1 | ~48s | 每样本独立启动 SPU session |
| batch=4 | ~25s（预估） | 4 样本共享 session |
| batch=8 | ~21.5s | 8 样本共享 session（当前最优） |

> 对于乡村医院，单次就诊通常只有 1-2 张影像，batch=1 是实际使用场景。
> 但如果是一次性上传多张影像等待结果，batch=8 效率更高。

### 3. 剪枝激进度

当前默认的剪枝比例为三阶段分别保留约 75%、50%、34% 的 token。
可以通过调整剪枝比例，在更早阶段丢弃更多 token，减少后续计算量。

| 保留比例（stage1/2/3） | 预估精度影响 | 预估速度提升 |
|------------------------|-------------|-------------|
| 75% / 50% / 34%（默认） | 基线 | 基线 |
| 60% / 40% / 25% | -1~2% | +10~15% |
| 50% / 30% / 20% | -3~5% | +20~30% |

### 4. Token 回收（recycle）

当 token 被剪枝时，将其加权信息注入 CLS token 以减少信息损失。
关闭此功能可略微提升速度，精度影响很小。

| 配置 | sec/sample | argmax一致率 | 说明 |
|------|-----------|-------------|------|
| recycle=0.1（开启） | 95.0s | 0.875 | 保留被剪枝 token 的部分信息 |
| recycle=0（关闭） | ~93s（预估） | ~0.875 | 关闭回收，精度基本持平 |

## 推荐配置方案

### 方案 A：高性能服务器（城市三甲医院）

适用于：CPU 核心数 ≥ 64，内存 ≥ 128GB，网络带宽充裕

```bash
export E2E_STATIC_DEPTH_LIMIT=-1          # 使用全部 12 层
export E2E_SPU_BATCH_SIZE=8               # 批量 8 样本
export E2E_SPU_TOKEN_RECYCLE_SCALE=0.1    # 开启 token 回收
```

预期性能：
- 推理速度：~21 秒/样本
- 阈值准确率：~92%
- 适合场景：大批量筛查、日常门诊

### 方案 B：中等配置服务器（县级医院）

适用于：CPU 核心数 16~32，内存 32~64GB

```bash
export E2E_STATIC_DEPTH_LIMIT=10          # 使用 10 层，跳过最后 2 层
export E2E_SPU_BATCH_SIZE=4               # 批量 4 样本
export E2E_SPU_TOKEN_RECYCLE_SCALE=0      # 关闭 token 回收
```

预期性能：
- 推理速度：~30 秒/样本（预估）
- 阈值准确率：~91%
- 适合场景：日常门诊、单次少量影像

### 方案 C：低配服务器（乡村卫生院）

适用于：CPU 核心数 4~8，内存 8~16GB

```bash
export E2E_STATIC_DEPTH_LIMIT=8           # 使用 8 层，跳过最后 4 层
export E2E_SPU_BATCH_SIZE=1               # 单样本推理
export E2E_SPU_TOKEN_RECYCLE_SCALE=0      # 关闭 token 回收
```

预期性能：
- 推理速度：~60~80 秒/样本（预估）
- 阈值准确率：~88%
- 适合场景：单次就诊、少量影像

### 方案 D：极端低配（离线/边缘设备）

适用于：无高性能服务器，通过网络调用远程推理服务

在这种场景下，乡村卫生院不需要本地部署模型，而是通过网络调用模型提供方的安全推理服务。
模型提供方的服务器承担全部计算，乡村卫生院只需上传影像数据的两份秘密份额。

- 推理速度：取决于网络延迟 + 模型提供方服务器性能
- 阈值准确率：与方案 A 相同（~92%）
- 适合场景：完全没有服务器条件的基层医疗机构

## 精度-效率权衡曲线

```
精度(阈值准确率)
  ^
  |
92|----● 方案A (depth12, batch8, 21s)
  |     \
91|      ● 方案B (depth10, batch4, ~30s)
  |       \
88|        ● 方案C (depth8, batch1, ~70s)
  |         \
85|          ● 极限裁剪 (depth6, batch1, ~50s)
  |
  +----+----+----+----+----+----> 推理速度(秒/样本)
      20   40   60   80  100
```

## 部署建议

1. **默认使用方案 A**：在硬件条件允许时，始终优先使用完整配置以获得最高精度。
2. **逐步降级**：如果服务器负载过高导致响应时间不可接受，按 A→B→C 的顺序逐步降低配置。
3. **方案 D 作为兜底**：对于完全没有服务器条件的基层机构，通过网络调用模型提供方的推理服务是最佳选择。
4. **未来优化方向**：针对低配服务器，可以考虑模型蒸馏（用小模型替代大模型）或量化（降低数值精度）进一步压缩计算量。

## 代码入口

所有配置均通过环境变量控制，无需修改代码：

```bash
# 运行入口
bash artifacts/server_inference_friendly_pack/run_e2e_secure_whole_forward.sh smoke8

# 关键环境变量
E2E_STATIC_DEPTH_LIMIT    # Transformer 深度限制，-1 为全量
E2E_SPU_BATCH_SIZE        # 批量大小
E2E_SPU_TOKEN_RECYCLE_SCALE  # token 回收比例，0 为关闭
```
